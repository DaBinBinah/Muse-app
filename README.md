# Muse-app

我把微信工作群交给 AI 了。

每天几千条微信消息，让 AI 先替我读一遍。每天早上 8 点，它会给我一份简报：昨天群里发生了什么、哪些事要处理、谁在等我回复、我应该怎么回。

这是一个让 Linux 微信在 [Muse.ai](https://muse.ai) 沙盒上常年在线的工具——不是因为这个玩法本身多有趣，而是因为它是整件事的地基。

## 起因

做 ERP / 信息化工作的应该都有体感：手机里同时挂着十几个工作群。项目群、实施群、开发群、财务群、供应链群、销售群、管理层群，还有各种临时拉的问题群。每天几百上千条消息，真正重要的可能就十几条。

烦的不是消息多，是你不知道哪十几条重要。只能一个个群翻，找 @自己的，找别人提的问题，判断哪些要跟进。一天下来，时间不是花在工作上，是花在捞消息上。

后来我就想，为什么不让 AI 先替我把微信读一遍？读完直接告诉我：什么事重要、谁在等我、我应该怎么回。

## 这个工作流怎么跑

要让 AI 持续读微信，前提是微信得一直在线。我的做法是把 Linux 微信装进 Muse 的沙盒里——AI 就住在同一台机器上，微信对它来说是个随时能读、每天都在更新的信息源。这跟每次复制一段聊天记录丢给 AI 总结，完全是两回事。

但这里有个坑：Muse 的沙盒会不定期整机重装，有点像机房电脑的还原卡。系统里装的东西全部消失，只保留家目录。微信一被重装就没了，工作流也就断了。

所以我写了 Muse-app，专门解决这一环：让沙盒里的微信打不死。

## Muse-app 具体干了什么

说穿了就三层东西。

第一，备用仓库。微信官方安装包加上 140 多个依赖包（一共 145MB），提前全部搬进家目录。家目录是重建后唯一幸存的地方，所以以后重装不靠网络，断网也能装回来。

第二，一个幂等的恢复脚本。所谓幂等，就是跑一百遍和跑一遍效果一样，重复执行不出乱子。它一上场就按固定顺序干活：先把机器的 machine-id 恢复成重建前的值（这个很关键，微信很拿这个当设备指纹，不恢复的话每次重建都把你当新设备），然后装依赖、装微信、起虚拟显示、起微信，最后把巡逻体系也修好。

第三，两个闹钟，互为备份。机器里面一个 cron，每分钟看一眼进程，微信挂了就地拉起来；机器外面还有个平台定时任务，每分钟检查一次，发现整机被重建了就叫恢复脚本上场。平时完全安静，只有真出事了才通知我，不会来烦人。

实际效果：进程挂了，1 分钟内回来；整机重建了，2 分钟左右自动恢复，脚本会自己把登录按钮点掉。我要做的只剩手机上点一次"确认登录"，不用扫码——试过固定 machine-id 想把这一下也省掉，没成功，这是微信自己的设备安全策略。另外平台夜里也会重建（我经历过一晚五次），想完全无人值守得换思路，GUI 微信这条路的天花板就在这。

有一条红线写在所有脚本里：绝不碰 `~/.xwechat`，也就是微信的数据和登录态。整个方案能成立，靠的就是这块东西重建后还在，谁都不许动它。

## Linux 微信能干什么、不能干什么

先把丑话说在前面：Linux 微信不是完整的微信。

能干的：群聊、@人、发文字语音图片视频文件、群接龙、语音转文字、看公众号、刷朋友圈、文件传输助手。日常沟通和看内容，够了。

不能干的：支付、红包、转账、银行卡，凡是跟钱沾边的都没有。

我反而觉得这是个优点。AI 在这个环境里接触的是信息和沟通，碰不到钱，所以它的定位是"工作沟通终端"，而不是替你操作微信的全部。当然话说回来，这不代表绝对没有账号或平台层面的其他风控，只是金融误操作这条最大的风险，被客户端本身挡掉了。

## 我最终想要的东西：每天 8 点的群日报

Muse-app 只是地基，地基上面怎么玩才是重点。比如让 Agent 每天早上 8 点自动出一份简报：

```text
☀️ ERP 微信工作简报

昨日消息：3,286 条
真正重要：27 条
需要处理：8 条 | 需要回复：5 条 | 需要跟进：4 条
无关闲聊：已过滤
```

简报里 AI 干的活是降噪，把几千条消息分成几类：

- 要我回答的：附上问题原文，顺便把回复帮我拟好
- 要我拍板的：背景、对方的意见、影响面，摆好等我决定
- 要跟进的：昨天有人说今天给测试环境，今天就得提醒我确认
- 知道就行的：一句话带过
- 废话：收到、好的、哈哈哈，直接滤掉

最有用的是第一类。群里有人问"这个订单为什么还不能审核"，AI 不光告诉我有人在等，还把回复拟好了："我先确认一下审核流程的配置，确认后回复你。"

这样每天早上花五分钟，扫一眼简报、看几个待办、发几条已经拟好的回复，几千条消息就处理完了。

我不指望 AI 替我工作。它能把每天重复出现的信息噪音先处理掉，就已经值回票价了。

## 想用的话

把这句话发给你的 Muse Agent：

```
帮我安装 https://github.com/DaBinBinah/Muse-app ，安装这个skills并开始执行。
```

SKILL.md 是完整的部署手册。部署过程中需要你动手的，就是首次下载依赖时点几次平台的审批卡（我不做任何自动批准这种事），加上微信登录的手机确认。装完手册里自带一个 60 秒的模拟演练，跑通了就可以等真实重建来验收。

DEPLOYED.md 是我自己部署的完整实录，包括踩过的坑。这个仓库里最值钱的可能不是代码，是那份实录——每条规则背后都是一次真实的翻车。

## 几个常见问题

**重建后要重新登录吗？** 电脑这边全自动，恢复完脚本自己点登录；手机上要确认一下，不用扫码。固定 machine-id 省掉手机这一下的尝试实测失败了——那是微信的设备安全策略，绕不过去。

**费 token 吗？** 沙盒里的 cron 不耗任何东西。费的是平台定时任务，每分钟唤起一次 Agent，一天 1440 次。额度紧张就放宽到 5 分钟一次，代价只是重建后晚几分钟被发现，沙盒内的巡逻还是每分钟照跑。

**微信升级了怎么办？** 换新安装包之后要把依赖缓存重做一遍（SKILL 里有命令），不然重建后断网就装不回来了。

**平台行为变得奇怪怎么办？** 先怀疑 machine-id 回写干扰了平台对沙盒的识别。把恢复脚本里那段回写去掉再观察，DEPLOYED.md 里有完整的排查预案。
