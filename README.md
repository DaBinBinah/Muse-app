# Muse-app

> 让 Muse.ai 沙盒里的 **Linux 微信"打不死"**：平台怎么重启、怎么重建，微信都会在约 3 分钟内自动恢复，聊天数据与登录状态全程不丢。
>
> A persistence & auto-restore toolkit for running Linux WeChat on Muse.ai sandboxes — survives platform rebuilds, keeps your login state, and contains **zero platform-policy-bypassing components**.

## 解决什么问题

Muse.ai 的沙盒是一台云上 Linux 虚拟机，平台会不定期**整机重建**（相当于学校机房的"还原卡"）：系统目录全部清空，只保留家目录 `/home/hatch`。于是——

- 系统里装好的微信每次重建都消失，要人肉重装；
- 重装后微信把你当"新设备"，又要扫码 / 手机确认；
- 微信一掉线，挂在微信上的事（客户群运营、消息通知……）就全断了。

实测确认：微信的数据与登录态（`~/.xwechat`）和官方安装包都位于家目录，**重建带不走它们**——缺的只是"自动装回来 + 自动启动"这一步。Muse-app 补的就是这一步。

## 工作原理（三层保险）

```
             ┌─ 沙盒内 cron（每分钟，零 token）── 看门狗 ─┐
 闹钟（双保险）┤                                            ├──→ 恢复脚本 restore-wechat.sh（幂等）
             └─ 平台定时任务（每分钟，跑在沙盒外）──────────┘          │
                                                                   ├ 0. 等平台装包锁释放（≤10 分钟）
 家目录（重建幸存）                                                  ├ 1. 回写 machine-id（防"新设备"判定）
   ~/workspace/installers/  ← 离线仓库：微信 deb + 142 个依赖包        ├ 2. 离线整批装依赖（断网可用）
   ~/.xwechat               ← 微信数据与登录态（红线，绝不触碰）       ├ 3. 装微信 → 起 Xvfb → 起微信
   ~/workspace/setup/*.sh   ← 恢复脚本与看门狗                        └ 4. 重建 cron 巡检线
```

- **进程挂了**（机器还在）：看门狗 1 分钟内拉起；
- **整机重建**：平台任务 1 分钟内发现 → 恢复脚本约 2 分钟跑完 → 微信回来；
- **重建后你要做的**：大概率什么都不用；最多手机微信上**点一次"确认登录"**（无需扫码；machine-id 回写就是为了让这一步也消失，见 FAQ）。

## 快速开始

把本仓库 `SKILL.md` 的 raw 链接发给你的 Muse Agent：

```
帮我安装 https://raw.githubusercontent.com/DaBinBinah/Muse-app/main/SKILL.md 并开始执行。
```

之后按手册节奏走，你只需在少数几个点介入：首次下载依赖时点几次平台审批卡（本方案**不自动批**）、微信登录的手机确认。部署完做一次手册自带的 60 秒模拟演练，然后就可以等真实重建来验收了。

## 使用场景（真实案例）

作者用一台 Muse 沙盒跑 Linux 微信做客户群运营（盯群、定时发新品、每日群简报）。部署 Muse-app 后微信 7×24 在线：平时零维护，平台重建后自动恢复，运营链路不再因重建而中断。

## FAQ

**Q1：重建后微信要手机确认吗？**
数据目录幸存时通常免扫码；多数情况手机上点一下"确认登录"即可。machine-id 回写就是为了让这一步也消失——但这属于微信设备安全策略的边界，无法从服务器端 100% 保证。

**Q2：耗 token 吗？**
沙盒内 cron 零消耗；只有平台定时任务每次唤起 Agent（每分钟一次 ≈ 1440 次/天）。额度吃紧可放宽到 5 分钟，代价仅是"重建后被发现"晚几分钟（沙盒内巡检仍每分钟照旧）。

**Q3：微信升级怎么办？**
换新 deb 后必须重做依赖闭包缓存（SKILL 步骤 2），否则重建后断网装不回。

**Q4：平台行为异常（定时任务不触发）？**
第一怀疑 machine-id 回写干扰了平台对沙盒的识别：去掉恢复脚本的 0d 段观察，`DEPLOYED.md` 有完整回滚预案。
